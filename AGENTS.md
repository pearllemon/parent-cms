# Editorial OS — always-on portfolio site instructions

Any change to text that readers or search engines encounter is a content change, regardless of whether the request says "SEO", "fix conversions", "add a feature", "improve", "next round", "publish", or "rewrite".

Before changing text: resolve site voice, audience, evidence, goal and current page; preserve strong passages. After changing: read actual final output, check accuracy, intent, useful specifics, attribution and commercial next step. For small UI labels, use a proportionate quick review; for articles, service pages and personal stories use a substantive narrative review. Do not invent experience, clients, metrics, credentials, quotes, endorsements or case studies. Avoid wordy AI boilerplate, interchangeable template pages, SEO keyword stuffing and mechanical FAQs. Never force Deepak's first-person memoir voice onto unrelated brands.

Use the private Pearl Lemon Editorial OS / editorial-guardian skill when available. If it is not available, enforce these local instructions. Do not treat the GitHub linter as evidence of human editorial approval.

Preserve URL/canonicals, metadata intent, analytics, forms, signups, schema, accessibility and existing SEO assets. Only deploy after normal checks. For WordPress and Lovable out-of-band publishing, GitHub CI does not intercept independent edits; enforce at that publishing system separately.
